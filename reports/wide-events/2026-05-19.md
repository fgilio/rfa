## Findings

### [WARNING] Updater canonical events omit rfa.duration_ms

- **File:** `app/Providers/NativeAppServiceProvider.php:92-96`, `app/Providers/NativeAppServiceProvider.php:127-131`
- **Rule:** Mechanics > Canonical Info Events. "Canonical events include `rfa.duration_ms`. There are no duration exemptions."
- **Evidence:** Both `updater.available` and `updater.downloaded` flush context, add `rfa.update_version` and `rfa.outcome`, then call `Log::info()` with no `rfa.duration_ms` field.
- **Impact:** The skill specifies that listener-owned events measure the callback when no operation start time exists. Querying logs for slow updater callbacks is impossible.
- **Suggested fix:** Record `$startedAt = microtime(true)` at the top of each callback and add `rfa.duration_ms` before the `Log::info()` call.

### [WARNING] updater.failed has no canonical info event

- **File:** `app/Providers/NativeAppServiceProvider.php:147-161`
- **Rule:** Mechanics > Errors And Criticals. "`Log::error()` is diagnostic. It never replaces the owner canonical info event."
- **Evidence:** The `UpdateError` listener flushes context, sets `rfa.outcome = error` and `rfa.reason = updater_error`, and emits `Log::error('updater.failed', ...)`, but no companion `Log::info()`.
- **Impact:** Success and failure paths of the updater callback are not represented symmetrically. A canonical-event query for updater outcomes will miss the failure branch.
- **Suggested fix:** Either emit `Log::info('updater.failed')` in a `finally` block (and downgrade the `Log::error()` to only the extra diagnostic detail), or restructure the three updater handlers behind a shared owner that emits one canonical event per check.

### [WARNING] Raw exception message stored in canonical context

- **File:** `resources/views/pages/⚡review-page.blade.php:507`
- **Rule:** Privacy. Anti-pattern list literally shows `Context::add('rfa.error', $e->getMessage());`.
- **Evidence:** `softRefresh()` catch block calls `Context::add('rfa.error', $e->getMessage())` before rethrow, which surfaces a raw exception message on the canonical `review.refreshed` event.
- **Impact:** Exception messages can include absolute paths, SQL, stderr, or user data. Leaks into a long-lived local log file.
- **Suggested fix:** Drop the `rfa.error` field. Keep `rfa.error_class` (line 508) and add a stable `rfa.reason` code per the standard's pattern.

### [WARNING] updater.failed payload leaks raw upstream message and stack

- **File:** `app/Providers/NativeAppServiceProvider.php:151-155`
- **Rule:** Privacy. Warning/error payloads avoid raw stderr and raw exception messages.
- **Evidence:** The payload includes `'message' => $event->message` and `'stack' => $event->stack` straight from the NativePHP `UpdateError` event.
- **Impact:** Upstream messages frequently embed absolute paths, hostnames, and HTTP details from the Electron updater. These persist in `storage/logs/laravel.log`.
- **Suggested fix:** Replace `message` with a sanitized short summary (truncated, path-redacted) and drop `stack` or hash it. Keep the `reason` code as the queryable field.

### [WARNING] Git warnings include raw exception messages

- **Files:**
  - `app/Actions/EnsureRfaGitExcludeAction.php:52`, `app/Actions/EnsureRfaGitExcludeAction.php:76`
  - `app/Actions/OpenProjectFromPathAction.php:28`
  - `app/Actions/ResolveBranchBaseAction.php:82`
  - `app/Services/GitMetadataService.php:25`, `app/Services/GitMetadataService.php:152`, `app/Services/GitMetadataService.php:175`, `app/Services/GitMetadataService.php:194`, `app/Services/GitMetadataService.php:218`, `app/Services/GitMetadataService.php:263`, `app/Services/GitMetadataService.php:334`
  - `app/Services/SyntaxHighlightService.php:183`
- **Rule:** Mechanics > Warnings. Warning payloads avoid raw exception messages and prefer stable reason codes plus sanitized detail.
- **Evidence:** All listed sites pass `'error' => $e->getMessage()` (or similar) directly into the warning payload.
- **Impact:** Git and highlighter exception messages routinely include absolute paths and command fragments. Reasoning over the logs requires reading free-form text instead of querying stable fields.
- **Suggested fix:** Drop `error`, keep `reason`, and add narrow structured fields (e.g. `error_class`, a sanitized one-line summary, the failing argument by name).

### [WARNING] Warnings expose raw stderr

- **Files:** `app/Actions/GetProjectStatusAction.php:31`, `app/Actions/LoadFileDiffAction.php:47`
- **Rule:** Mechanics > Warnings. "Warning payloads avoid raw file contents, raw stderr, secrets, and avoidable absolute paths." Good example uses `stderr_summary`.
- **Evidence:** Both sites attach `'stderr' => $e->stderr`.
- **Impact:** Git stderr can contain absolute paths, ref names, and process output that adds noise without aiding debugging beyond the reason code.
- **Suggested fix:** Sanitize and truncate via a `stderr_summary` field (first line, path-redacted, capped to a few hundred chars), matching the standard's example.

### [WARNING] Several warnings include absolute repo paths under `repo`

- **Files:** `app/Actions/EnsureRfaGitExcludeAction.php:54,78`, `app/Actions/ResolveBranchBaseAction.php:84`, `app/Services/GitMetadataService.php:27,154,177,196,220,265,336`, `app/Actions/GetProjectStatusAction.php:30` (as `repoPath`)
- **Rule:** Privacy. Absolute paths are allowed in warning payloads "only when no project context can resolve a relative path or when the path itself is the failed input being diagnosed." Repo root is reachable as a project slug at all of these call sites.
- **Evidence:** Each payload includes the absolute repo root rather than a project slug or hash.
- **Impact:** Local-only logs still embed `/Users/.../path/to/repo` style strings on every git fallback.
- **Suggested fix:** Either pass a project slug down (preferred) or hash the repo path. Note: `OpenProjectFromPathAction.php:30` is the exception, since the failed input IS the path being registered, which fits the standard's carve-out.

### [INFO] Default log channel is `single` with `LOG_LEVEL=debug`

- **File:** `config/logging.php`, `.env`
- **Rule:** Storage [Review SHOULD]. Standard prefers `daily` with bounded retention and `info` level.
- **Evidence:** `LOG_CHANNEL=stack`, `LOG_STACK=single`, `LOG_LEVEL=debug`. The `single` channel writes `storage/logs/laravel.log` with no rotation. CI test C8 still passes because no remote handler is active in the resolved default.
- **Impact:** Local log file grows unboundedly. `debug` level is noisier than intended (no production code emits debug logs today, so the practical noise is bounded by framework deprecation warnings).
- **Suggested fix:** Flip the default to `daily` with `days=7` and `LOG_LEVEL=info`, matching the example block in the standard.

## Clean Areas

- Event names are lowercase dot-separated with 2 to 3 segments (CI test passes).
- All static `Context::add()` keys are namespaced under `rfa.` (CI test passes).
- All warning and error payloads include a `reason` field (CI test passes).
- All `Log::info()` calls pass a single literal event name with no manual context array (CI test passes).
- `review.refreshed` in `⚡review-page.blade.php:480-541` follows the prescribed `Context::flush()` plus `try/catch/finally` template, sets `rfa.outcome` and `rfa.duration_ms`, and ships rich IDs, counts, and booleans for debugging.
- Updater listeners (`NativeAppServiceProvider`) flush context before adding fields, so they do not leak state between callbacks in the long-lived renderer process.
- Child warnings emitted from actions and services use inline payloads instead of `Context::add()`, preserving owner correlation.
- No `Log::debug()` in production code, no duplicate canonical event between parent and child for `review.refreshed`.
- No remote logging channels are active in the resolved default stack (`stack` -> `single` writing to `storage/logs/laravel.log`); CI check C8 is satisfied.
- `context.comment.rejected` is appropriately a warning (the rejection guards against renderer state drift, not a normal user rejection) and uses an enum-backed stable reason code.
- `RuntimeDiagnosticsService` writes a separate JSONL breadcrumb file and is not a `Log::*` call, so it is outside the wide-events surface. It already redacts URL paths, hashes repo paths, and bounds payload size.

## Residual Risks

- Agentic ownership review for git-related warnings assumes each call site is invoked from a path that already has a logged owner (the `review.refreshed` flow or a future page-level canonical). Spot checks on `LoadFileDiffAction` (called from `softRefresh`) confirm this. Sites like `GitMetadataService::getCommitLog` are called from `GetCommitHistoryAction`, which currently has no canonical owner in the audit surface; a future audit pass should verify the commit-history flow has an owner.
- The audit only inspected files surfaced by the inventory ripgrep. New canonical events added outside `app/` and `resources/views/` would be missed.
- The `OpenProjectFromPathAction` "project opened" operation is not represented by any canonical `Log::info()` today. The action is called from listeners that record `RecordRuntimeDiagnosticAction` JSONL breadcrumbs only. This is borderline between "missing canonical owner" and "intentionally diagnostic-only," and was not raised as a finding pending product judgement.
- The CI default-channel check passes because Laravel's stack expands to `single`. If `LOG_STACK` were ever changed via env to include `slack`, `papertrail`, or similar, the test would catch it, but per-environment overrides are not audited here.
