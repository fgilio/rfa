## Findings

### [WARNING] Canonical info events missing `rfa.duration_ms`

- **File:** `app/Providers/NativeAppServiceProvider.php:96`, `app/Providers/NativeAppServiceProvider.php:131`
- **Rule:** Canonical Info Events. `rfa.duration_ms` is required on every canonical event, with no exemptions for near-instant operations.
- **Evidence:** The `UpdateAvailable` and `UpdateDownloaded` listeners set `rfa.update_version` and `rfa.outcome` before emitting `updater.available` and `updater.downloaded`, but never measure or attach a duration.
- **Impact:** Loses the per-event timing baseline that the standard guarantees, so a regression in updater latency cannot be diagnosed from logs alone.
- **Suggested fix:** Record `microtime(true)` at listener entry and attach `rfa.duration_ms` to `Context::add()` before the canonical `Log::info()`. The standard explicitly states listener-owned events should measure the callback when no operation start time is available.

### [WARNING] `updater.failed` is logged only as `Log::error`, with no canonical `Log::info`

- **File:** `app/Providers/NativeAppServiceProvider.php:151`
- **Rule:** Errors And Criticals. "`Log::error()` is diagnostic. It never replaces the owner canonical info event."
- **Evidence:** The `UpdateError` listener flushes Context, sets `rfa.outcome = 'error'` and `rfa.reason = 'updater_error'`, then emits `Log::error('updater.failed', ...)` only. No corresponding `Log::info()` is emitted.
- **Impact:** The update operation has no canonical info row in this path, so error and success outcomes for the same unit of work do not share an event name. Querying logs for "all updater attempts and outcomes" requires reading two distinct event streams.
- **Suggested fix:** Emit a canonical `Log::info('updater.failed')` with the same Context fields (and add `rfa.duration_ms`). Keep `Log::error('updater.failed', [...])` only if extra diagnostic detail beyond the canonical event is genuinely needed, otherwise drop it.

### [WARNING] Raw exception message added as `rfa.error` context field

- **File:** `resources/views/pages/⚡review-page.blade.php:513`
- **Rule:** Privacy. "Do not log raw exception messages unless they are known safe or redacted. Exception messages often contain absolute paths, SQL, stderr, or user data."
- **Evidence:** `Context::add('rfa.error', $e->getMessage());` in the `softRefresh` catch block.
- **Impact:** Any exception thrown during refresh leaks its raw message into the canonical `review.refreshed` event, including potentially absolute paths, sql fragments, or git internals.
- **Suggested fix:** Drop `rfa.error` and rely on `rfa.error_class` plus a stable `rfa.reason` code. If a free-form snippet is genuinely needed, redact it first.

### [WARNING] Raw `$event->message` and `$event->stack` in `updater.failed` payload

- **File:** `app/Providers/NativeAppServiceProvider.php:153-154`
- **Rule:** Privacy. Raw exception messages and raw stderr-like blobs are disallowed in warning and error payloads.
- **Evidence:** `'message' => $event->message, 'stack' => $event->stack` are forwarded verbatim from the auto-updater event.
- **Impact:** Updater error messages and stack traces routinely contain absolute paths, version URLs, and OS internals that the wide-events standard treats as private and noisy.
- **Suggested fix:** Capture a short `summary` (truncated, single-line, classifier-friendly) instead of `message`, and drop or summarize `stack`. Reserve raw detail for a separate diagnostic path that is not the canonical log.

### [WARNING] Raw stderr forwarded in git warning payloads

- **File:** `app/Actions/GetProjectStatusAction.php:31`, `app/Actions/LoadFileDiffAction.php:47`
- **Rule:** Warnings. Warning payloads "avoid raw file contents, raw stderr, secrets, and avoidable absolute paths." The standard's good example uses a `stderr_summary` field name to signal sanitization.
- **Evidence:** Both call sites pass `'stderr' => $e->stderr` directly from `GitCommandException` (see `app/Exceptions/GitCommandException.php:13`), which holds the unfiltered git process output.
- **Impact:** Git stderr can contain absolute repo paths, hostnames, and remote URLs. The unfiltered payload is also unbounded in size, hurting log retention budgets.
- **Suggested fix:** Add a small helper that returns a single-line truncated `stderr_summary` (cap at e.g. 240 chars) and use it consistently. Rename the field to `stderr_summary` so the contract is explicit.

### [WARNING] Avoidable absolute repo paths in warning payloads

- **File:** `app/Actions/GetProjectStatusAction.php:30` (`repoPath`), `app/Actions/ResolveBranchBaseAction.php:84` (`repo`), `app/Actions/EnsureRfaGitExcludeAction.php:54, 78` (`repo`), `app/Services/GitMetadataService.php:27, 152, 175, 203, 227, 272, 346` (`repo`)
- **Rule:** Privacy. "Absolute paths are allowed in warning payloads only when no project context can resolve a relative path or when the path itself is the failed input being diagnosed."
- **Evidence:** Every git-warning payload above includes the full absolute `$repoPath` as `repo` or `repoPath`. The callers already know a project context (slug or id) for these failures.
- **Impact:** Every git warning leaks an absolute on-disk path to logs even when a project slug would identify the repo equivalently. This is also the largest single source of avoidable PII-shaped data in current logs.
- **Suggested fix:** Plumb `project_slug` (or `project_id`) into these warnings and drop the absolute `repo` field, or hash it. Where the call site truly has no project context, keep the absolute path but rename it `repo_path_absolute` so it is grep-able.

### [WARNING] Raw exception messages forwarded as `error` in warning payloads

- **File:** `app/Actions/OpenProjectFromPathAction.php:39`, `app/Actions/ResolveBranchBaseAction.php:87`, `app/Actions/EnsureRfaGitExcludeAction.php:55, 79`, `app/Services/GitMetadataService.php:28, 155, 177, 205, 229, 273, 347`, `app/Services/SyntaxHighlightService.php:250, 547`
- **Rule:** Privacy plus Warnings. The standard's anti-patterns block explicitly calls out `'rfa.error' => $e->getMessage()` and `'stderr' => $e->stderr` as patterns to remove.
- **Evidence:** Every warning payload above includes `'error' => $e->getMessage()`. These exceptions originate from git process failures, file IO failures, or third-party syntax highlighter exceptions, all of which routinely embed absolute paths and ref names in their messages.
- **Impact:** Same leakage profile as raw stderr, with the added problem that exception classes are not stable so the `error` strings are also useless as a query key.
- **Suggested fix:** Replace with `'error_class' => $e::class` plus the existing `reason` string. If a short message is needed, take the first line and truncate.

### [WARNING] Default local log channel is noisier and less bounded than the standard recommends

- **File:** `config/logging.php:21, 61-66`, `.env.example:18-21`
- **Rule:** Storage. The `[Review SHOULD]` block recommends `daily` with `level=info` and 7-day retention.
- **Evidence:** `'default' => env('LOG_CHANNEL', 'stack')` and `LOG_STACK=single` resolve to the `single` channel, which has no rotation and defaults `level` to `debug`. `LOG_LEVEL=debug` is the env default.
- **Impact:** Local file grows without rotation in long-lived NativePHP installs. Debug level is louder than intended and can mask the canonical wide-event signal.
- **Suggested fix:** Either switch the default to `daily` with `days=7` and `level=info`, or change the `single` channel definition to use `'level' => env('LOG_LEVEL', 'info')` and add a retention story (e.g. set defaults to daily in production). Slack and papertrail definitions can stay; they are correctly not active in the default stack.

### [INFO] No canonical event for `OpenProjectFromPathAction` success path

- **File:** `app/Actions/OpenProjectFromPathAction.php:19`
- **Rule:** Logging Ownership. "Action owns the canonical event when a Livewire component or listener delegates the operation to an action." The standard names `project.opened` as a good event name.
- **Evidence:** The success branch returns the registered project with no log emission. Only the unexpected-error branch emits a warning.
- **Impact:** No record of project open operations in logs. Cannot trace which projects were opened via the deep-link/menu entry points, or how often, without reading database state.
- **Suggested fix:** Add a canonical `Log::info('project.opened')` with `rfa.outcome` (`completed`, `rejected` for `NotAGitRepositoryException`, `error` for unexpected), `rfa.project_slug`, `rfa.project_id`, `rfa.duration_ms`, and `rfa.path_hash`.

### [INFO] No canonical event for `LoadFileDiffAction`

- **File:** `app/Actions/LoadFileDiffAction.php:34`
- **Rule:** Logging Ownership. The standard names `diff.loaded` explicitly as a good event name.
- **Evidence:** The action returns success or a fallback FileDiff array with no canonical `Log::info()`. Warnings fire only on git failure.
- **Impact:** No per-file load telemetry to support latency or cache-hit/miss debugging.
- **Suggested fix:** If per-file granularity is too noisy at scale, scope the canonical event to cache misses only (with `rfa.cache_hit` boolean) and tag with `rfa.duration_ms`, `rfa.outcome`, `rfa.byte_count`, `rfa.path` (relative). Otherwise emit unconditionally.

### [INFO] No canonical event for `GetProjectStatusAction` success path

- **File:** `app/Actions/GetProjectStatusAction.php:22`
- **Rule:** Logging Ownership.
- **Evidence:** Returns the status array silently on success; only the git-failure path emits a warning.
- **Impact:** No event corresponds to the externally meaningful "status checked for project X" operation, so canonical correlation between project-status warnings and successful calls is impossible.
- **Suggested fix:** Add `Log::info('project.status.loaded')` with `rfa.project_slug`, `rfa.file_count`, `rfa.outcome`, `rfa.duration_ms`. Consider gating behind a cache-miss boolean if this is invoked frequently from the UI.

## Clean Areas

- The four-test arch suite at `tests/Arch/LoggingConventionsTest.php` enforces no `Log::debug` in production, info logs without inline arrays, dotted lowercase event names with 2 to 4 segments, and `reason` on every warning/error payload. All four pass.
- `Context::flush()` is correctly called before `Context::add()` in every logging-owner block reviewed (`NativeAppServiceProvider` listeners and `softRefresh` on the review page).
- Child services do not duplicate parent canonical events. `GitMetadataService`, `SyntaxHighlightService`, and the git-touching actions only emit warnings, never canonical info events for an operation owned by a caller.
- Storage: the default `stack` resolves only to `single` by default. `slack` and `papertrail` are defined but not active in the default channel or stack. The `browser` channel is local file only. No remote handlers are reachable from the resolved default.
- `rfa.outcome` values seen in code (`completed`, `error`) are inside the approved vocabulary. No invalid literals were observed.
- Event names follow the lowercase dotted past-tense convention (`updater.available`, `updater.downloaded`, `updater.failed`, `review.refreshed`, `project.registration.failed`, `git.commit_range.list_failed`, etc.).
- Warning payloads include stable `reason` keys consistently.

## Residual Risks

- Agentic ownership review is limited to call-site reading. A full call-chain trace was not performed for each warning emitter, so a hypothetical child warning whose owner is several layers up could be misclassified as orphaned.
- The audit did not run the app and inspect actual emitted log lines, so payload sizes for `stderr` and `error` fields are inferred from source rather than measured.
- The audit did not enumerate every Livewire component method that performs a user-facing side effect. There may be additional missing canonical events beyond the three actions flagged under `[INFO]`.
- `LOG_LEVEL` and `LOG_STACK` are resolved from the `.env` file at runtime. Built installer artifacts may override the `.env.example` defaults. The Storage finding is based on the example template only.
- `rfa.outcome` literals like `partial`, `cancelled`, `skipped`, and `rejected` are part of the standard vocabulary but were not observed in code. This is consistent with current behavior, not a violation.
