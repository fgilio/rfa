## Findings

### [WARNING] Canonical event carries a raw exception message

- **File:** `resources/views/pages/⚡review-page.blade.php:507`
- **Rule:** Privacy ([Agent MUST] no raw exception messages), A9, and the documented anti-pattern `Context::add('rfa.error', $e->getMessage())`
- **Evidence:** The error path of `softRefresh` does `Context::add('rfa.error', $e->getMessage())`, so the raw message lands on the `review.refreshed` canonical event emitted in `finally`.
- **Impact:** Exception messages routinely embed absolute paths, SQL, and stderr. This is the exact pattern the standard lists as forbidden, and it puts unredacted data on the most-queried event.
- **Suggested fix:** Drop `rfa.error`. Keep `rfa.error_class` and add a stable `rfa.reason` code instead.

### [WARNING] Raw stderr in warning payloads

- **File:** `app/Actions/LoadFileDiffAction.php:47`, `app/Actions/GetProjectStatusAction.php:30`
- **Rule:** Privacy ([Agent MUST] warnings avoid raw stderr), A9
- **Evidence:** Both warnings pass `'stderr' => $e->stderr` directly. The standard's own good example uses `'stderr_summary' => $sanitizedSummary`.
- **Impact:** Raw git stderr can contain absolute paths and file fragments, and it is unbounded in length, which adds noise to local logs.
- **Suggested fix:** Replace `stderr` with a sanitized, length-capped `stderr_summary`.

### [WARNING] Raw exception messages in warning payloads

- **File:** `app/Actions/EnsureRfaGitExcludeAction.php:55`, `:79`, `app/Actions/OpenProjectFromPathAction.php:31`, `app/Actions/ResolveBranchBaseAction.php:87`, `app/Services/GitMetadataService.php:155`, `:177`, `:205`, `:229`, `:274`, `:343`, `app/Services/SyntaxHighlightService.php:246`, `:479`
- **Rule:** Privacy ([Agent MUST] no raw exception messages unless known safe or redacted), A9
- **Evidence:** Each of these warnings passes `'error' => $e->getMessage()`. For the git sites the source is a `GitCommandException` whose message typically wraps the failed command and its stderr.
- **Impact:** Same exposure as raw stderr. Messages can leak absolute paths and command fragments, and they vary per run so they make poor stable signals.
- **Suggested fix:** Replace raw messages with a stable `reason` plus the already-present `rfa.error_class` style identifier, or a sanitized summary. Most of these already carry a `reason` code, so the raw message can be dropped.

### [WARNING] Updater canonical events omit rfa.duration_ms

- **File:** `app/Providers/NativeAppServiceProvider.php:96` (`updater.available`), `:131` (`updater.downloaded`)
- **Rule:** Canonical Event Fields, A6 ([Agent MUST] canonical events include `rfa.duration_ms`, no exemptions)
- **Evidence:** Both listeners flush context, add `rfa.update_version` and `rfa.outcome`, then emit a canonical info event. Neither records `rfa.duration_ms`.
- **Impact:** The standard states there are no duration exemptions and that listener-owned events should at least measure the callback. Missing the field makes these two events inconsistent with the canonical contract and unqueryable by duration.
- **Suggested fix:** Capture `microtime(true)` at the start of each callback and add `rfa.duration_ms` before the `Log::info` call.

### [WARNING] Updater error log carries raw message and stack trace

- **File:** `app/Providers/NativeAppServiceProvider.php:151`
- **Rule:** Privacy ([Agent MUST] no raw exception messages or avoidable absolute paths), A9
- **Evidence:** `Log::error('updater.failed', ...)` passes `'message' => $event->message` and `'stack' => $event->stack`.
- **Impact:** Updater stack traces and messages can include absolute install paths and update-server URLs. The `stack` field is unbounded raw diagnostic text on a local log.
- **Suggested fix:** Drop `stack`, and either omit `message` in favor of the existing `reason` code or pass a sanitized, length-capped summary.

### [WARNING] Default log channel is unbounded and debug level

- **File:** `config/logging.php:21`, `:61`
- **Rule:** Storage ([Review SHOULD] default resolves to local daily files with bounded retention and `info` level), audit Storage check on unbounded retention and noisier-than-intended default
- **Evidence:** `default` resolves to `stack`, whose `LOG_STACK` default is `single`. The `single` channel writes one file with no `days` cap and defaults its level to `debug` via `env('LOG_LEVEL', 'debug')`. The standard's recommended default is `daily` with `days => 7` and `info`.
- **Impact:** Out of the box the active channel keeps one ever-growing file at debug verbosity, which is both unbounded and noisier than the standard intends. Remote channels remain inactive, so this is not critical, and packaging env may override it.
- **Suggested fix:** Point the default at a bounded `daily` channel with `days => 7` and default the level to `info`, or set `LOG_STACK`/`LOG_LEVEL`/`LOG_DAILY_DAYS` accordingly in the packaged env.

### [INFO] Comment-add operations have no canonical owner event

- **File:** `resources/views/pages/⚡context-page.blade.php:256`, comment writes in `resources/views/pages/⚡review-page.blade.php`
- **Rule:** Logging Ownership and Warning And Error Semantics (rejected inputs should be represented by an owner canonical event with `rfa.outcome = rejected`)
- **Evidence:** `addContextComment` only emits `context.comment.rejected` on the failure path and has no canonical `Log::info` for the success path. The review-page comment write methods emit no canonical event either. The only instrumented canonical event in these pages is `review.refreshed`.
- **Impact:** If a comment write is considered an externally meaningful unit of work, its outcomes are not queryable as one canonical event, and the rejected path is signalled by a standalone warning rather than `rfa.outcome = rejected`. This is a coverage judgment, not a rule violation, since the rejection here is described as unexpected renderer-state drift, which legitimately warrants a warning.
- **Suggested fix:** Decide whether comment writes are an owner operation. If yes, add a canonical event with `rfa.outcome` covering completed and rejected paths. If no, leave the warning as is.

## Clean Areas

- C1 holds: no `Log::debug()` in `app/` or `resources/views`.
- All warning payloads include a stable `reason` code (C5), and `context.comment.rejected` uses an enum-backed reason value.
- All static `Context::add()` keys use the `rfa.` namespace (C4), and no banned absolute-path keys appear (C7).
- Event names are lowercase dot-separated past-tense literals within two to four segments (C3, A8): `review.refreshed`, `updater.available`, `updater.downloaded`, `updater.failed`.
- `review.refreshed` is a strong canonical event: it flushes first, sets `rfa.outcome` and `rfa.duration_ms`, and carries rich IDs, counts, and booleans for debugging.
- Logging ownership is clean. Child actions and services emit only warnings or one handled error and do not duplicate the parent canonical events (A1, A2).
- Storage stays local. The resolved default stack reaches only the `single` file channel. Slack, papertrail, syslog, errorlog, and stderr definitions exist but are inactive (C8).

## Residual Risks

- Absolute repo roots appear as `repo`/`repoPath` values in several git warnings. The standard permits absolute paths in warnings when no project slug is available or the path is the failed input, which fits these service-layer sites, so they are not flagged. A reviewer may still prefer threading a slug through.
- Agentic review reads excerpts around each log site. Indirect data flow into `$e->getMessage()` or `$event->message` was inferred from exception types, not traced end to end.
- The storage finding assumes the default env values in `config/logging.php`. Packaged-release env files were not inspected and may already override `LOG_CHANNEL`, `LOG_STACK`, and `LOG_LEVEL`.
- `rfa.duration_ms` presence was confirmed by inspection of the three canonical events only. No runtime log output was examined.
